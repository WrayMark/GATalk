# GATalk 使用文档规范

## 目标

让第一次使用 GATalk 的美术从业者可以边看界面边完成操作，不需要先阅读产品背景
或实现原理。

## 内容结构

每个主要工作流按以下顺序编写：

1. 用途：一句话说明该功能解决什么问题。
2. 入口：说明从哪个工作台、页签或按钮进入。
3. 操作：通常 3 至 6 个短步骤，每步只做一件事。
4. 结果：说明保存或生成了什么。
5. 注意：只保留数据安全、费用、真实性边界和不可逆操作。

## 图片规则

- 首页、全局设置和每个主要工作台至少各有一张当前版本截图。
- 图片只保留理解当前步骤所需的界面；过宽界面可以裁剪，但不得隐藏关键上下文。
- 图注直接说明用户应观察的位置，不使用“如下图所示”等无信息文字。
- 截图使用简体中文、默认深色主题和可读字号。
- 不显示 API Key、用户姓名、私人路径、真实团队机密或无授权作品。
- 使用合成测试图片或仓库内可分发素材，截图脚本必须可重复运行。
- UI、术语或入口变化时重拍受影响图片；禁止继续复用已过期截图。

## 文字规则

- 优先使用动作动词，例如“导入”“选择”“保存”“运行”“导出”。
- 一个步骤只表达一个动作；一般不超过两行。
- 不解释代码、Schema、线程或内部目录，除非用户必须依赖这些信息排错。
- 不重复描述同一功能；常用规则集中到“通用操作”。
- 主手册保持简洁；详细算法、架构和验证记录放在 `docs`。
- 中文与英文说明同步维护；其他界面语言不要求单独生成手册。

## 交付检查

1. 运行 `scripts/capture_user_guide_screenshots.py` 更新截图。
2. 运行 `scripts/build_user_guide_docx.py` 生成 Word 手册。
3. 渲染 Word 文档并逐页检查图片清晰度、文字截断、分页和图注。
4. 运行自动化测试和 `git diff --check`。
